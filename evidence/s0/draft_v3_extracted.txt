Development of a Credit Card Default Risk Prediction System Using Machine Learning Classification Algorithms
Executive Summary
This project develops a complete risk prediction system for credit card defaults using machine learning classification algorithms. Financial institutions need reliable ways to identify customers who might miss their upcoming monthly payments so that early support and payment plans can be offered. Our four member team analyzed the Default of Credit Card Clients dataset from the UCI Machine Learning Repository, which contains thirty thousand customer records across twenty five attributes. We cleaned and verified the dataset, conducted exploratory data analysis across six visual charts, and trained three classification models to predict payment defaults on an independent test set. We then built an interactive web application using Streamlit and a secure SQLite database to deploy the best performing pipeline with separate Admin and User roles. Among the tested models, the Decision Tree classifier provided the best overall balance with an accuracy of 81.72 percent, a precision of 66.15 percent, a recall of 35.49 percent, and an F1 score of 46.20 percent, fulfilling all twelve system verification tests within our fourteen day schedule.
1. Introduction and Project Scope
1.1 Background and Problem Statement
The main problem is that financial institutions lose money when customers default on their monthly credit card payments. Predicting these payment defaults early allows banks to take preventive actions like offering flexible payment plans before a customer falls into deep debt. A bank officer can review a customer payment history and flag accounts that show early signs of financial stress, such as delayed payments over the past two months or rising bill balances. Manual reviews take too much time when a bank manages tens of thousands of active cardholders every month. This project solves the problem by creating a machine learning prototype that automates the risk prediction process and provides clear recommendations as a decision support tool for bank staff.

Using historical data recorded prior to the prediction month ensures that the input features would actually be available to a bank officer when a real prediction is made, which completely avoids data leakage. 2.3 Data Cleaning and Preprocessing Pipeline Justification
We conducted a thorough data cleaning and preprocessing workflow before training our classification models. Justifying each cleaning step ensures that our machine learning pipeline is scientifically sound and free from preprocessing leakage. First, we inspected all thirty thousand rows for missing cells and duplicate entries, verifying that the dataset contains zero missing values and zero duplicate records. Second, we dropped the ID column and separated the target column default.payment.next.month from the twenty three remaining input features. Third, we split the dataset into an 80 percent training set of 24,000 records and a 20 percent testing set of 6,000 records using stratified sampling so that both sets maintain the exact same proportion of default cases. Fourth, we applied Scikit learn StandardScaler to normalize all twenty three features to a mean of zero and a variance of one, fitting the scaler strictly on the 24,000 training records and applying the learned transformation to the 6,000 test records so that test data never leaks into model training.
3. Exploratory Data Analysis
3.1 Target Variable Distribution and Class Imbalance Calculation
We explored the data visually to understand the underlying patterns and class balance before training our models. Exploring the target variable distribution helps us identify class imbalances that could distort model accuracy and guide our choice of evaluation metrics. As shown in Figure 2, out of 30,000 total customers, 23,364 customers paid their credit card bills on time in Class 0 and 6,636 customers defaulted on their next payment in Class 1. To calculate the exact percentage for On Time Class 0, we divide 23,364 by 30,000 and multiply by 100 to get 77.88 percent. To calculate the exact percentage for Default Class 1, we divide 6,636 by 30,000 and multiply by 100 to get 22.12 percent. Because almost four times as many customers pay on time as default, evaluating models on accuracy alone would be misleading, so we must focus closely on recall and F1 score for the default class.

4. Machine Learning Methodology and Development
4.1 Six Step Machine Learning Training Workflow
We followed a strict six step machine learning methodology to train and compare our three classification models fairly. Using a standardized workflow ensures that no test data leaks into preprocessing and that all models are judged on the exact same unseen records. As illustrated in Figure 8, we loaded and verified the 30,000 records, selected the 23 eligible historical features, and performed a stratified 80 percent training and 20 percent testing split. In the 6,000 record test set, stratified splitting preserved 4,673 On Time Class 0 records or 77.88 percent and 1,327 Default Class 1 records or 22.12 percent. We then fitted StandardScaler on the 24,000 training rows and trained Logistic Regression, Decision Tree with maximum depth 5, and Random Forest with 100 trees and maximum depth 5.

Figure 8: Six Step Machine Learning Training and Evaluation Workflow
4.2 Step by Step Mathematical Evaluation Calculations
In our binary classification task, Default Class 1 is designated as the positive class because the business goal is to identify customers at risk of defaulting. Every model is evaluated on the 6,000 unseen test records using four core metrics derived from the confusion matrix: Accuracy, Precision, Recall, and F1 Score. True Positives are actual defaults correctly predicted as Default, True Negatives are on time payers correctly predicted as On Time, False Positives are on time payers wrongly predicted as Default, and False Negatives are actual defaults missed by the model. Below is the complete step by step working calculation process for all three models.
First, we compute the complete working calculations for the Logistic Regression baseline model using its test confusion matrix counts in Figure 9, where True Negatives equal 4,528, False Positives equal 145, False Negatives equal 1,009, and True Positives equal 318. Step 1 Accuracy: We add True Positives of 318 and True Negatives of 4,528 to get 4,846 total correct predictions. We then divide 4,846 by 6,000 total test records to get 0.807667, which rounds to 0.8077 or 80.77 percent. Step 2 Precision: We add True Positives of 318 and False Positives of 145 to get 463 total predicted defaults. We then divide 318 by 463 to get 0.686825, which rounds to 0.6868 or 68.68 percent. Step 3 Recall: We add True Positives of 318 and False Negatives of 1,009 to get 1,327 total actual defaults in the test set. We then divide 318 by 1,327 to get 0.239638, which rounds to 0.2396 or 23.96 percent. Step 4 F1 Score: We multiply 2 times Precision of 0.686825 times Recall of 0.239638 to get the numerator 0.329179. We add Precision of 0.686825 and Recall of 0.239638 to get the denominator 0.926463. We then divide 0.329179 by 0.926463 to get 0.355307, which rounds to 0.3553 or 35.53 percent.
Second, we compute the complete working calculations for the Decision Tree model using its test confusion matrix counts in Figure 10, where True Negatives equal 4,432, False Positives equal 241, False Negatives equal 856, and True Positives equal 471. Step 1 Accuracy: We add True Positives of 471 and True Negatives of 4,432 to get 4,903 total correct predictions. Step 2 Precision: We add True Positives of 471 and False Positives of 241 to get 712 total predicted defaults. We then divide 471 by 712 to get 0.661517, which rounds to 0.6615 or 66.15 percent. Step 3 Recall: We add True Positives of 471 and False Negatives of 856 to get 1,327 total actual defaults. We then divide 471 by 1,327 to get 0.354936, which rounds to 0.3549 or 35.49 percent. Step 4 F1 Score: We multiply 2 times Precision of 0.661517 times Recall of 0.354936 to get the numerator 0.469592. We add Precision of 0.661517 and Recall of 0.354936 to get the denominator 1.016453. We then divide 0.469592 by 1.016453 to get 0.461991, which rounds to 0.4620 or 46.20 percent.

5.2 Database Schema, Role Security, and Admin Functions
The system architecture includes a secure SQLite database that manages user accounts, role permissions, and prediction logs. A simple role selector dropdown without authentication is not real access control, so our application stores passwords as secure SHA256 hashes and enforces role permission checks on every privileged page. Ordinary users can only access the credit risk prediction form and view their results. Admin users have exclusive access to the account management dashboard, where they can create new users or update roles, as well as the dataset upload validator, which checks uploaded CSV files to ensure all twenty five required columns and numerical data types are present before accepting the file.
5.3 Model Pipeline Integration and Action Recommendation Engine
We used the Joblib library to load the saved best_pipeline.joblib artifact directly inside the Streamlit prediction module. Integrating the complete pipeline guarantees that new customer numbers typed into the web form are scaled using the exact same StandardScaler parameters learned during training before reaching the Decision Tree classifier. When the user clicks the predict button, the pipeline outputs both the binary class prediction and the estimated probability of default via predict_proba. The application then matches the probability score against the four tier rule table shown in Table 12 to display a clear interpretation and a practical banking action recommendation on the screen.

6.2 Critical Discussion of Model Performance and Errors
The system correctly rejects invalid data inputs and generates accurate predictions, but a thorough critical discussion must examine the model errors observed on the test set. Because the UCI dataset contains 77.88 percent on time payers and only 22.12 percent defaulters, all three classifiers face a natural pull toward the majority class. On the 6,000 test records, our selected Decision Tree model correctly identified 4,432 on time payers and 471 defaulters, while producing 241 False Positives and 856 False Negatives. The 241 False Positives represent customers who actually paid on time but were flagged as at risk, which only results in a polite payment reminder or supportive phone call. In contrast, the 856 False Negatives represent customers who had clean payment records in previous months but suddenly defaulted, meaning a 35.49 percent recall score still misses customers whose financial trouble begins abruptly without prior billing delays.
6.3 Ethical Considerations, Data Privacy, and Project Limitations
We must also consider the ethical implications and technical limitations of deploying machine learning models in consumer finance. Financial and demographic data is highly sensitive, and automated credit risk systems must never be used to discriminate against customers based on gender, age, or marital status. Our prototype addresses this ethical responsibility by relying primarily on objective repayment status codes for over 85 percent of its decision weight and by framing every output as a supportive recommendation for payment assistance rather than an automated penalty. Regarding limitations, the current prototype relies on a local SQLite database and a single historical dataset from 2005, which is completely sufficient for a two week academic demonstration but would require encrypted enterprise database hosting and updated local banking records before commercial deployment.
7. Conclusion and Future Work
7.1 Conclusion
This project successfully developed a complete, functioning Credit Card Default Risk Prediction System within the fourteen day deadline. We met all six project objectives by verifying and preprocessing the thirty thousand record UCI Credit Card dataset, interpreting six exploratory data analysis charts, and comparing Logistic Regression, Decision Tree, and Random Forest models on an independent test set. Selecting and integrating the Decision Tree pipeline into our role protected Streamlit and SQLite application provided reliable predictions, probability estimates, and actionable recommendations for financial risk management. Our structured four member team approach and early Day 8 model integration ensured that all workstreams and all twelve verification tests were completed on time.
7.2 Future Work and System Enhancements
Future work should focus first on improving the model recall score for the default class so that fewer at risk customers are missed. We can apply class balancing techniques like Synthetic Minority Over sampling Technique or cost sensitive class weights during training alongside probability threshold tuning to raise recall above 60 percent. We also recommend migrating the local SQLite database to a secure cloud database platform with multi factor authentication. Finally, adding a visual prediction history analytics dashboard and local feature explanation charts would further enhance the usefulness of the Admin and User modules.
