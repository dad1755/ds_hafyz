## §2 The page — read at the code site, and the table it renders

`src/pages_admin.py:297` `render()` calls `_guard()` first (`:51-54`), which is
`security.require_role(conn, token, ("admin",), action="pages_admin.render")`. The page then offers
`_create_form` (`:105`), `_manage_one` per account (`:164` — display-name form, role selectbox,
temporary-password form with confirm, and the Deactivate/Reactivate button pair), `_table` (`:80`)
and `_audit_panel` (`:265`).

The list is built from `accounts.UserView` (`src/accounts.py:45-56`), whose fields are `id`,
`username`, `display_name`, `role`, `is_active`, `must_change_password`, `created_at`, `updated_at`,
`last_login_at` — **there is no hash field to render**, which is a stronger property than "the
template does not print it". The rendered columns, read off the live element tree rather than the
source, are:

```
['username', 'display name', 'role', 'active', 'must change password', 'created (UTC)', 'last sign-in (UTC)']
```

`src/accounts.py:73-76` also excludes the hash from the SELECT list (`_USER_COLUMNS`), so it is not
merely unrendered — it is never read into the page process.

## §4 One transaction per write, one audit row per write

| Function | Transaction | Audit row |
|---|---|---|
| `create_user` (`:152`) | `with transaction(conn):` at `:172`, INSERT at `:173` | `audit.append(..., "user.created", ...)` at `:187` inside it |
| `set_role` (`:204`) | `:219` | `"user.role_changed"` at `:232` |
| `set_active` (`:244`) | `:257` | `"user.deactivated"` / `"user.activated"` at `:277` |
| `set_display_name` (`:289`) | `:308` | `"user.display_name_changed"` at `:313` |
| `reset_password` (`:325`) | `:339` | `"password.reset"` at `:349` |

`audit.append` takes the caller's connection and runs inside the caller's transaction
(`src/audit.py:73-99`), so a write and its audit row commit or roll back together — there is no
"audited but not applied" or "applied but not audited" window. The real audit trail from this
verifier's run, showing one row per write in order:

```
   13 actor=1 user.created               user:3 {"role":"user","username":"gate_created"}
   14 actor=1 user.display_name_changed  user:2 {"from":"gate_user","to":"Renamed By Gate","username":"gate_user"}
   15 actor=1 user.role_changed          user:2 {"from":"user","to":"admin"}
   16 actor=1 user.role_changed          user:2 {"from":"admin","to":"user"}
   17 actor=1 password.reset             user:2 {"forced_change":true,"username":"gate_user"}
   18 actor=1 user.deactivated           user:2 {"username":"gate_user"}
   19 actor=1 user.activated             user:2 {"username":"gate_user"}
```

`reset_password` additionally revokes every live session of the target and sets
`must_change_password = 1` in the same transaction (`src/accounts.py:339-348`), so a reset takes
effect immediately instead of at the victim's next sign-in.

## §6 Admin role is restricted; there is no self-registration

* Anonymous: `app.py` renders `pages_login.render_login` only — two text inputs (`Username`,
  `Password`) and one button (`Sign in`); no sidebar, so no navigation to reach.
* A signed-in user: the sidebar options are `Home`, `Predict default risk`, `My prediction
  history`; `User management` is appended only when `principal.role == "admin"` (`app.py:198-200`).
  This is convenience, not the control — §3 is the control.
* Self-registration: `grep -rniE "register|sign[_ -]?up" app.py src/` returns nothing, and there is
  no `render_register` in `src/pages_login.py`. The only account-creating path in the application is
  `accounts.create_user`, which is admin-gated at `src/accounts.py:163`.

## §7 The installation cannot be orphaned, and nothing is deleted

Both escape hatches are refused at the service layer, not in the UI (`src/accounts.py:225` and
`:262` re-count `role='admin' AND is_active=1` inside the same transaction as the write, so two
administrators demoting each other concurrently cannot both succeed):

```
2. Last enabled administrator cannot be orphaned
  [PASS] demote last admin — refused: The last enabled administrator cannot be demoted.
  [PASS] deactivate last admin — refused: The last enabled administrator cannot be deactivated.
  [PASS] admin still admin and active
```

There is no delete path at all: `accounts` exposes no `delete_user`/`remove_user`/`purge_user`
(asserted by attribute probe), `grep -rn "DELETE FROM users"` finds nothing anywhere in the tree, and
`tests/test_admin.py:607` asserts the same. Deactivation is soft — the row, its audit history and its
predictions stay.

## §9 No hash and no plaintext in the audit table, the database or the logs

After every write in §3–§5, this verifier swept the finished database (`gate_probe.txt`, §7):

```

  [PASS] no plaintext in audit_events
  [PASS] no plaintext anywhere in the SQL dump
  [PASS] no hash in audit_events

```

"Exactly once" is the informative one: each Argon2id hash appears in `users.password_hash` and
nowhere else in the dump — not in `audit_events`, not in `sessions`, not in `predictions`.

The audit table's defence is by construction, not by caller discipline: `audit.sanitise_details`
(`src/audit.py:43-70`) drops any key matching
`(pass(word|wd|phrase)|hash|token|secret|cookie|session|authorization|credential|api[_-]?key|private[_-]?key)`
and records only a `redacted_fields` count, and truncates long strings to 120 characters so a pasted
secret cannot land whole. `src/audit.py` exposes no update and no delete function.

**Logs** — a throwaway container from the real S8 image, on no network, with a disposable database;
