## 3. Limitations, stated plainly

1. **`scripts/verify_release.sh` did not finish.** It printed 13 consecutive PASS lines at the tag
   (§6) and then stopped inside the 14th check, `docker run … test -r /app/models/best_pipeline.joblib`,
   where the daemon accepts `create` and never starts the container. A control probe of the same
   command at 00:0xZ still exits **124** after 60 s, and `docker ps -a` shows **26** containers left
   in `Created` by several different agents. This is a host-wide stall, not a property of the release.
   The three checks it was there to prove were re-proved with `docker exec` and `docker image inspect`
   instead (§4), which exercise the same container with the same user.
2. **The pytest suite was not re-run.** It needs `docker run` and therefore the same blocked path.
   It is not evidence-free: no application code changed between `49540a6` — where the S13 gate ran
   the suite — and `v1.0.0` (0 `.py` files in the diff), and the image is byte-identical to the tag.
   The gap is a re-run, not a coverage hole.
3. **The operator's `.env` credential no longer signs in.** `INITIAL_ADMIN_PASSWORD` is 7 characters
   and the seeded account carries `must_change_password = 0` with a compliant password set later, so
   `init_admin.py` correctly never rewrote it — two sign-in attempts with the `.env` value returned
   *Invalid username or password* (recorded in `login_attempts`). The both-roles smoke therefore used
   a synthetic admin and a synthetic user created for the run and **deactivated afterwards**
   (`qa_s16_gate_admin` id 9, `qa_s16_gate_user` id 10, both `is_active = 0`). Operational note for
   handover: the operator must know their own rotated password; `.env` is not it.
