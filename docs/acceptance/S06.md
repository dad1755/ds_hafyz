## 3. Storage inspection, executed by the verifier

Read through the app's own opener (`src.db.connect`) and through a read-only URI connection, against
the live `/app/storage/aihubcampus.db`:

```
== connection policy (via src.db.connect, the app's only opener) ==
  PRAGMA journal_mode = wal
  PRAGMA busy_timeout = 5000
  PRAGMA foreign_keys = 1
  PRAGMA synchronous = 1

tables: ['audit_events', 'dataset_versions', 'login_attempts', 'prediction_logs',
         'schema_migrations', 'sessions', 'sqlite_sequence', 'users']
migrations: [('0001_core_tables', '2026-10-26T10:58:32Z'),
             ('0002_auth_sessions', '2026-10-26T10:58:32Z')]

accounts (prefix and length only — no hash is printed anywhere in this record):
  username=ds_hafyz    role=admin active=True  must_change_password=True   hash_prefix=$argon2id$ hash_len=97
  username=demo_user   role=user  active=True  must_change_password=False  hash_prefix=$argon2id$ hash_len=97
distinct hash prefixes: ['$argon2id$']
```

Two independent checks that the pragmas are real and not just defaults of my own connection:

- `foreign_keys=0` is what a plain `sqlite3.connect()` reports on the same file, and `1` is what
  `src.db.connect()` reports — so the `ON` comes from the code path, not from the interpreter.
- an orphan insert is actually refused: `IntegrityError: FOREIGN KEY constraint failed`.

Code review of the same claims: `src/db.py:201-205` sets `journal_mode=WAL`, `busy_timeout`,
`foreign_keys=ON` and `synchronous=NORMAL` on every connection; `transaction()` (`src/db.py:208-222`)
uses `BEGIN IMMEDIATE`; `migrate()` (`src/db.py:237-257`) records each version in `schema_migrations`
inside its own transaction and skips versions already applied; every statement in `src/db.py`,
`src/security.py`, `src/accounts.py` and `src/audit.py` is parameterised — the only interpolated SQL
in the tree is `PRAGMA busy_timeout={BUSY_TIMEOUT_MS}` (`src/db.py:202`) and the `SELECT
{_USER_COLUMNS}` column list in `src/accounts.py`, both built from module constants, never from user
input. Hashing is
`argon2id` with `time_cost=3`, `memory_cost=64 MiB`, `parallelism=4`, 32-byte hash, 16-byte salt
(`src/security.py:82-86, 181-185`); there is no SHA-256 password path in the tree.

## 8. The headline controls, re-executed live by the verifier

Beyond the suite, the verifier drove each control directly against a copy of the live database:

```
== wrong password, then right password ==
  login(user, wrong password): InvalidCredentials: Invalid username or password.
  login(user, right password): OK -> 'demo_user'

== a forced password change blocks every privileged call ==
  admin signed in, must_change_password=True
  accounts.list_users while a change is pending: PasswordChangeRequired: A password change is required before this account can continue.
  after change_password: must_change_password=False
  accounts.list_users after the change: OK -> ['demo_user', 'ds_hafyz']

== the last enabled admin cannot be demoted or deactivated ==
  set_role(admin -> user): PolicyViolation: The last enabled administrator cannot be demoted.
  set_active(admin -> False): PolicyViolation: The last enabled administrator cannot be deactivated.
  admin row before=('admin', 1) after=('admin', 1) unchanged=True

== logout revokes the session row ==
  resolve_session after logout: SessionInvalid: Your session has ended. Sign in again.

== deactivated user is blocked at sign-in, and their live session dies ==
  resolve_session on the session opened before deactivation: SessionInvalid: Your session has ended. Sign in again.
  login(user, right password) while deactivated: AccountInactive: This account is not active. Contact the administrator.
  login(user) after reactivation: OK -> 'demo_user'

== session expiry is absolute ==
  resolve at +7h59m: OK -> 'demo_user'
  resolve at +8h01m: SessionInvalid: Your session has ended. Sign in again.

== the throttle fires after 5 failures, and a correct password does not bypass it ==
  attempt 1: InvalidCredentials: Invalid username or password.
  attempt 2: InvalidCredentials: Invalid username or password.
  attempt 3: InvalidCredentials: Invalid username or password.
  attempt 4: InvalidCredentials: Invalid username or password.
  attempt 5: InvalidCredentials: Invalid username or password.
  attempt 6: Throttled: Too many failed sign-in attempts. Try again in 15 minutes.
  correct password during the lockout: Throttled: Too many failed sign-in attempts. Try again in 15 minutes.
  failed attempts recorded for that username: 5
```

Two details worth recording because they are easy to get wrong and are right here: the throttle is
checked **before** the password is verified, so a correct password does not clear a lockout; and a
forced password change blocks `require_role` itself, so an admin-set temporary password cannot be
used to browse the admin section.

## Findings

**F-1 — MEDIUM — carried owner item, not an S6 regression: two operator passwords remain in git
history.** `docs/acceptance/S01.md` quoted the two seeded passwords literally in the S1 record. They
are redacted in the tree at `1b1be9a`, but the blobs before that commit still contain them (2 commits
touch the file with each string; §6). *Acceptance-blocking?* **No, for merging S6 into a local `main`
of a repository with no remote** — nothing can fetch them, and the S6 control the card actually asks
for (no secret in a tracked file) passes. **Yes, for any push, mirror, archive or publication of this
repository**: rotate both passwords first, then either leave the history as is (it stays local) or
rewrite it with owner authorisation. Recorded as an owner act, as the card instructs; the gate does
not attempt a history rewrite.

**F-2 — LOW — `security.login()` returns a principal with `session_expires_at = None`**
(`src/security.py:555` returns `_principal_from_row(row, None)`; `login()` at `:558-579` creates the
session but returns that same principal). Any caller that reads the expiry from `login()`'s return
value gets `None`; this gate's own probe raised `AttributeError` on exactly that. No user-facing
defect today, because `app.py` re-resolves the session through `resolve_session()` on every rerun and
never renders the expiry from the login return. Suggested fix when S7 touches this file: return
`_principal_from_row(row, expires_at)` from `login()`, or resolve once after creating the session.

**F-3 — LOW — accepted trade-off, recorded for the record: the throttle is per username, not per
IP** (`src/security.py:268-275, 479-489`). An unauthenticated attacker who knows a username can lock
that account out for 15 minutes. `docs/architecture.md` §14 records the reasoning (the app sits behind
the tunnel and sees no trustworthy client address; no throttle is worse). Not a defect, but S12
should decide whether a per-IP or per-cookie counter is worth adding once the tunnel is live.

**F-4 — LOW — unrecorded deviation from the blueprint: the bootstrap admin username.** `blueprint.md`
§19, §9 SPRINT 6 and the project brief all say the initial admin username is `web`; the implementation
takes it from `INITIAL_ADMIN_USERNAME` (here `ds_hafyz`). The value is environment-only, which is the
stronger reading of "password from environment ONLY", and this card itself names `ds_hafyz` — so the
behaviour is right, but `docs/architecture.md` §9 has no decision row for it (D12–D14 cover the other
deviations). Add a D-row at S7 so an assessor comparing the blueprint to the build does not read it
as drift.

**F-5 — LOW — the audit trail stores attacker-typed text for an unknown username**
(`src/security.py:502-509` records `entity_id` = the normalised username). It is bounded to 64
characters by `_normalise_username` and a username is not a credential, but it does mean whatever
someone types into the username box of a failed sign-in is persisted in `audit_events`. A fixed
placeholder (`unknown`) for the unknown-user case would close the last place where unvalidated input
reaches storage.

No finding is a functional or security defect in the S6 deliverable itself; none blocks the merge.
