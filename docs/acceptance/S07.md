## §6 History isolation and honesty

Driven through the real pages with **two** accounts in one database:

```console
PASS  account A sees exactly its own row   [1]

PASS  anonymous list_predictions is refused   [SessionInvalid]
```

The reason it holds is structural, not a filter the caller could forget: `list_predictions(conn,
token)` resolves the user id from the session token inside the query and takes no user argument at
all, so passing `user_id=` raises `TypeError` (asserted). The page itself re-checks the session
before reading anything (`src/pages_history.py:46-50`) and again inside the call.

The page's notice is on screen: *"These are model outputs you requested, stored against your
account. A row does not mean a customer defaulted: the model is an observational estimate on
historical 2005 data, and its probabilities are uncalibrated."* The history columns are timestamp,
predicted class, estimated P(default), risk band and model version — no column states or implies a
real default.

## Findings

**F-1 — LOW — the §6 palette is not implemented; the UI uses Streamlit's default accent.**
`.streamlit/config.toml` has `[server]`, `[browser]` and `[client]` sections and **no `[theme]`**
section, and no page injects CSS, so the primary accent is Streamlit's default red
(`#FF4B4B`) — visible on the "Predict default risk" button, the selected sidebar radio and the
expander chevrons in every screenshot, including this gate's own captures.
`blueprint.md` §6 "UI style" asks for "navy/slate/teal neutral" with a white background; the white
background is right, the palette is not. No functional or security impact, and the verbatim
acceptance clause does not mention colour, so this does not block the merge — but it is an
unrecorded deviation from the spec, and the fix is a five-line `[theme]` block
(`primaryColor`, `backgroundColor`, `secondaryBackgroundColor`, `textColor`) in
`.streamlit/config.toml`. Recorded, not fixed, as this gate is read-only on product code.

**F-2 — LOW — the Home page does not carry the three explanation cards §6 asks for.**
`blueprint.md` §6: "Home includes 3 concise explanation cards: data, ML comparison, prediction."
`app.py:89-114` renders a "What this build contains" list and a "How to use it" paragraph instead.
This is S6-era home content, not something S7 introduced, and it is not on this card's work-item
list — recorded so an assessor comparing the build to the blueprint is not surprised. It belongs to
whichever sprint owns the Home page (§6 also puts the model-comparison summary there, which is S10).

**F-3 — MEDIUM — the running review stack is not serving S7; only the branch and the built image
are.** `docker inspect aihubcampus-web-1` reports image `sha256:71f0e68e5ecd…` =
`aihubcampus-web:local`, whose `/app/src` has no `pages_prediction.py`, `pages_history.py` or
`pages_login.py`, and whose `app.py` still says "Sprint 6 entry point"; it was started
2026-10-26T11:20:18Z, before `73d9825` was committed at 12:00Z. The S7 code is correctly built in
`aihubcampus-web:s7` (byte-identical to the tree). So anyone opening the compose `web` service today
sees the S6 build. This is not a code defect and not part of the acceptance clause, and this gate
did not redeploy it (read-only on the environment; the owner decides when the demo stack moves) —
but the review stack must be rebuilt and recreated (`docker compose up -d --build web`, one build at
a time) before S7 is demonstrated, or the demo will show the previous sprint.

**F-4 — informational, carried from the S6 record (F-2) and still open.**
`src/security.py:555` still returns `_principal_from_row(row, None)`, so a `Principal` returned by
`security.login()` carries no `session_expires_at`. No user-facing effect today: `app.py` re-resolves
the session through `resolve_session()` on every rerun and never renders the expiry from the login
return. S7 did not touch this file. Carried, not re-raised as an S7 finding.

**F-5 — informational — the duplicate-submission guard is per session, not per account.**
The fingerprint lives in the session map `st.session_state["prediction_seen"]`
(`src/pages_prediction.py:141,262-263`; `src/predictions.py:83,196-205`), so an accidental
double-click is caught, while a genuine resubmission from a second tab or a new session records a
new row. That matches "protect against accidental duplicate submissions" in §9 SPRINT 7; noted so
the behaviour is not mistaken for a uniqueness constraint on `prediction_logs`.

No finding is a functional or security defect in the S7 deliverable itself. F-1 and F-2 are
unrecorded spec deviations (cosmetic), F-3 is an operational gap in the review stack, and F-4/F-5
are carried or informational.

## Evidence-quality note

Every command, number and screenshot in this record was produced by this verifier on 2026-10-26
between 20:29 and 21:14 +08:00. The verifier's scripts (`verify_s7.py`, `qa_s7_browser.js`) live
outside the repository in a scratch directory and import only `src/`, `ml/` and the Streamlit test
harness; they read no file from `tests/` and no captured output from `evidence/s7/`. Two of the
verifier's own checks failed on the first attempt and were fixed in the *verifier's* script, not in
the product: a wrong assumption about `AppTest` form semantics (a form widget's `set_value` is
discarded unless the submit button is clicked in the same run) and a selector that read a
selectbox's label instead of its value. Both are disclosed here because the corrected checks are
what the PASS lines above come from.

Side effects of the verification, disclosed so the demo state is not a surprise: the verifier ran
one throwaway container (`aihubcampus-qa-s7`) of `aihubcampus-web:s7` on the project network with a
scratch storage directory, seeded with one disposable synthetic account, and removed it afterwards;
it published no host port and wrote nothing into `aihubcampus_app_storage`. All `AppTest` and data
probes used SQLite files in the container's own temporary directory. The pre-existing
`aihubcampus-web-1` container, its volume and its database were not modified.
