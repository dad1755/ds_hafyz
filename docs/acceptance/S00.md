## 5. Architecture: port coupling and threat model

`docs/architecture.md` §5 "Ingress resolution — the port 2026 decision" states the fact, the
options and the decision:

> "The operator's Cloudflare tunnel already publishes **both** `www.aihubcampus.online` and
> `aihubcampus.online` to **`http://web:2026`**. `blueprint.md` §2/§7 instead specify
> `http://web:8501` … **Decision (A).** The application serves on **2026**: `APP_PORT=2026` is the
> single source of truth; `.streamlit/config.toml` (`server.port`), the Dockerfile `CMD`, `EXPOSE`,
> the compose `expose:` entry and the healthcheck URL all derive from it."

The coupling is resolved by moving the app to the ingress's port instead of editing the tunnel
(option B, rejected as an unauthorised DNS/tunnel change; option C, a proxy container, rejected as a
second failure point). It keeps the compose service named `web`, forbids a `ports:` section, and
records the reversal path (`APP_PORT` is one value). It is also honest about provenance: the 2026
target is an operator report, **not independently verified in S0** (`~/.cloudflared` is empty —
confirmed by the verifier), with S13 to confirm against the live domain. Deviation is registered as
D1 in §9.

Threat model: §7 "Data sensitivity and threat model" present, with assets, actors, a 12-row threat
table T1–T12 (credential stuffing, privilege escalation, session hijack, secret disclosure,
malicious CSV upload, untrusted model artifact, SQL injection, public origin exposure, cross-user
exfiltration, harmful output, log leakage, DoS), each with control + residual risk, plus an explicit
compliance stance and a "fairness is not proven" limitation.
